# Inbox local acceptance — 2026-08-25

This run validates the Phase 1 inbox on one local macOS development machine, one Go API process, local PostgreSQL, and the two SvelteKit development servers. It is useful engineering evidence, but it is not the production-like Section 15 acceptance run: there was no deployment reverse proxy/TLS path, multi-instance fan-out, network latency, 10-minute sustained write window, or production infrastructure sizing.

## Dataset and safety

- Generated by `go run ./cmd/inbox-load-seed --confirm-local`.
- The command refuses `APP_ENV=production`, refuses a non-loopback PostgreSQL host, and replaces only dedicated `inbox-load-*@example.invalid` records.
- 10,334 conversations: 10,000 on one large provider and 334 isolated load/browser actors.
- 100,334 initial messages: 10 per large-provider conversation and one per isolated actor.
- 334 authenticated provider identities were allocated as 333 × 3 streams plus 1 × 1 stream, exactly 1,000 streams.
- Generated credentials and session headers were mode `0600` under `/tmp/tellbook-inbox-load`; they were not written to the repository.
- Post-seed ownership mismatches: 0. Conversations missing either participant state: 0.

## Defects found and fixed during the run

- The local scale fixture omitted canonical `marketplace_customer_identities`, so password fallback could not resolve seeded customer emails. The seeder now creates verified identity rows.
- After successful modal authentication, only the root session dependency was invalidated; `/messages` retained its unauthorized route payload until reload. Authentication now invalidates both the session and inbox-list dependencies.
- `MessagesScreen` copied its initial SSR list into local state only at construction. It now reconciles only when a genuinely new SSR inbox snapshot arrives, preserving ordinary render/realtime efficiency while allowing post-auth data to appear immediately.
- The load runner now supports a bounded `identity_limit` for smoke tiers and per-identity stream counts, allowing exactly 1,000 target streams without duplicating credentials.
